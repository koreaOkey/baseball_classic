## Context

현재 Android 홈 화면은 당일 경기 목록을 표시하고, 응원팀 기준의 다가오는 경기 3개를 별도 섹션으로 보여준다. 백엔드는 날짜 단위 경기 조회인 `GET /games?date=YYYY-MM-DD`를 제공하지만 팀/기간 단위 일정 API는 없다. 따라서 MVP는 기존 날짜별 조회를 재사용해 향후 30일 응원팀 경기를 모아 팝업으로 표시한다.

모바일 Android는 운영 중인 우선 플랫폼이고 iOS 모바일은 확장 예정 플랫폼이다. 워치 앱은 홈 일정 탐색 자체에는 직접 관여하지 않으며, 일정 항목에서 LIVE 경기를 선택했을 때 기존 경기 상세/동기화 흐름을 재사용한다.

## Goals / Non-Goals

**Goals:**
- 홈의 달력 영역을 응원팀 일정 팝업 진입점으로 만든다.
- Android 홈에서 향후 30일 응원팀 경기 전체를 bottom sheet로 확인할 수 있게 한다.
- 기존 날짜별 경기 조회와 경기 상세 진입 흐름을 재사용한다.
- 응원팀 미선택, 로딩, 오류, 일정 없음 상태를 UX로 처리한다.
- iOS 모바일에도 동일 UX 요구사항을 명세로 남긴다.

**Non-Goals:**
- 시즌 전체 일정을 위한 신규 백엔드 API를 이번 변경에서 만들지 않는다.
- DB 마이그레이션이나 크롤러 수집 범위 변경은 포함하지 않는다.
- 워치 앱 UI는 변경하지 않는다.
- 시스템 캘린더 동기화는 포함하지 않는다.

## Decisions

1. **기존 날짜별 경기 API를 재사용한다.**
   - 이유: 홈의 다가오는 경기 섹션이 이미 같은 방식으로 작동하며, MVP 구현 범위를 Android 앱으로 제한할 수 있다.
   - 대안: 팀/기간 전용 백엔드 API 추가. 장기적으로는 더 효율적이지만 이번 요청의 빠른 검증에는 과하다.

2. **팝업은 ModalBottomSheet 패턴을 사용한다.**
   - 이유: 홈의 전체 순위 팝업이 이미 같은 패턴을 사용하므로 사용자가 같은 상호작용 모델로 이해할 수 있다.
   - 대안: 별도 화면 전환. 일정 탐색만을 위해 홈 흐름을 끊는 비용이 크다.

3. **MVP 기간은 오늘 포함 향후 30일로 제한한다.**
   - 이유: 날짜별 API 반복 호출 수를 제한하면서 “전체 일정 확인”의 1차 체감 가치를 제공한다.
   - 대안: 시즌 전체 날짜를 반복 조회. 모바일 네트워크 비용과 로딩 시간이 커진다.

4. **응원팀 일정 항목은 기존 경기 모델과 상세 진입 콜백을 재사용한다.**
   - 이유: LIVE/FINISHED/SCHEDULED 상태별 진입 정책과 카드 표현이 기존 홈 흐름과 어긋나지 않는다.
   - 대안: 일정 전용 상세 화면. 이번 범위에서는 중복 구현이다.

## Risks / Trade-offs

- [날짜별 반복 조회로 초기 로딩이 느려질 수 있음] -> 30일 제한, 캐시 재사용, 로딩 상태 표시로 완화한다.
- [DB에 향후 일정이 충분히 수집되어 있지 않으면 팝업이 비어 보일 수 있음] -> 일정 없음 상태를 명확히 표시하고, 후속으로 팀/기간 API와 수집 범위 확대를 검토한다.
- [Android와 iOS 구현 시점 차이로 플랫폼 경험이 갈릴 수 있음] -> iOS spec과 task를 남겨 후속 구현 기준을 고정한다.
- [워치 동기화 흐름과 혼동될 수 있음] -> 일정 팝업은 모바일 탐색 기능으로 한정하고, 워치 앱은 변경하지 않는다.

## Migration Plan

1. Android 앱에 데이터 조회 확장과 홈 bottom sheet를 배포한다.
2. 백엔드/DB 변경이 없으므로 서버 롤백 절차는 필요하지 않다.
3. 문제가 있으면 홈 달력 탭 동작만 제거하거나 팝업 진입 상태를 비활성화해 기존 홈 경험으로 되돌릴 수 있다.

## Open Questions

- 시즌 전체 일정이 필요해지는 시점에 팀/기간 전용 API를 추가할지 결정해야 한다.
- iOS 모바일 구현 착수 시점과 SwiftUI 화면 구조를 별도로 확정해야 한다.
