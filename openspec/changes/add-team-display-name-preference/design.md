## Context

모바일 앱은 응원팀을 `DOOSAN`, `LG` 같은 팀 코드로 저장하고, 현재 UI 라벨은 각 플랫폼의 `Team.teamName`이 제공하는 마스코트명을 많이 사용한다. 워치 테마와 백엔드 구독 매칭은 팀 코드를 기준으로 동작하므로, 사용자가 보는 표시명만 별도 선호로 분리해야 한다.

비로그인 사용자도 팀 구독 푸시를 받기 때문에 서버 경기 시작 푸시는 `user_settings`만으로는 충분하지 않다. 푸시 토큰 및 팀 구독 등록 payload에 표시 방식 선호를 함께 저장해야 한다.

## Goals / Non-Goals

**Goals:**
- 팀 선택값과 표시 방식을 분리한다.
- 신규/기존 사용자 모두 표시 방식을 선택할 수 있게 한다.
- 모바일, 워치, 경기 시작 visible push가 같은 선호를 따른다.
- 구버전 클라이언트가 표시 방식을 보내지 않아도 안전하게 동작한다.

**Non-Goals:**
- 팀 코드, 경기 매칭, 테마 선택 기준을 바꾸지 않는다.
- 구단 공식 로고 자산이나 팀 테마 컬러 체계를 변경하지 않는다.
- Live Activity content-state에는 팀명 필드가 없으므로 이번 범위에서 변경하지 않는다.

## Decisions

1. **표시 선호는 `TEAM` / `MASCOT` 문자열로 저장한다.**
   - 대안: Boolean 저장. 확장성은 낮고 의미가 불명확하다.
   - 선택 이유: API/DB/클라이언트에서 의미가 명확하고 구버전 fallback을 단순하게 유지할 수 있다.

2. **`selected_team`은 계속 팀 코드로 유지한다.**
   - 대안: `selected_team`에 표시명을 저장. 백엔드 구독, 워치 테마, 캐시 키가 깨질 수 있다.
   - 선택 이유: 사용자 표시와 시스템 식별을 분리하는 것이 안전하다.

3. **서버 푸시는 토큰 단위 표시 선호로 그룹화한다.**
   - 대안: 사용자 설정 테이블만 조회. 비로그인 사용자와 토큰 기반 구독을 놓친다.
   - 선택 이유: 현재 경기 시작 푸시는 `team_subscription_tokens` 기반이므로 같은 테이블에 선호를 저장하는 것이 정확하다.

4. **워치에는 설정 업데이트로 표시 선호를 동기화한다.**
   - 대안: 경기 데이터의 home/away 문자열을 이미 변환해서 전송. 워치 독립 복원/캐시와 플랫폼별 fallback이 복잡해진다.
   - 선택 이유: 워치가 테마용 팀 코드와 표시용 문자열을 독립적으로 처리할 수 있다.

## Risks / Trade-offs

- 기존 클라이언트가 표시 선호를 보내지 않음 -> 서버 기본값을 `TEAM`으로 처리하고 nullable/기본 컬럼을 둔다.
- 워치가 오래된 설정을 들고 있을 수 있음 -> 모바일 앱 시작, 표시 선호 변경, 응원팀 변경 시 설정을 다시 동기화한다.
- 화면 전체의 모든 팀 라벨을 한 번에 교체하면 리스크가 큼 -> 우선 사용자-facing 주요 팀 라벨과 워치 스코어보드, 푸시를 적용하고 테스트로 회귀를 잡는다.

## Migration Plan

- DB 마이그레이션으로 관련 테이블에 `display_name_style` 컬럼을 추가하고 기본값을 `TEAM`으로 둔다.
- 백엔드는 요청 필드가 누락되면 `TEAM`으로 저장한다.
- 클라이언트는 로컬 기본값을 `TEAM`으로 등록하고, 서버 저장은 로그인 상태일 때 best-effort로 수행한다.
- 롤백 시 새 컬럼은 남겨도 기존 클라이언트/서버 동작에는 영향을 주지 않는다.

## Open Questions

- 없음. 사용자 결정: 적용 범위는 모바일+워치+서버 푸시, 신규 기본값은 팀명, 기존 사용자는 1회 팝업.
