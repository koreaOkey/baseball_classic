## Context

`redesign-live-game-detail-screen`(2026-05-22) 에서 경기 상세 화면을 6개 섹션 구조로 재정비했고, 2번째 섹션인 필드 프리뷰는 SwiftUI `Path` / Compose `Canvas` 로 직접 그린 단순 다이아몬드 + 루상 원 + 투수/타자 텍스트로 구현됐다. 같은 change 의 design.md Decision 2 / Non-Goal 에서 "필드 프리뷰는 현재 state 기반의 시각화로 제한", "실제 수비 위치/라인업 등은 후속 백엔드 보강 범위" 로 명시됐다.

사용자가 제공한 reference 이미지(`reference/경기 진행 카드.png`) 는 외야 잔디 + 다이아몬드 일러스트 위에 9명의 선수 사진과 이름을 포지션별로 띄운 형태다. 본 변경은 사진은 제외(KBO 라이선스 회피) 하고 **이름만** 노출하는 1단계로 시작한다.

higgsfield CLI 로 다크 톤 PNG 1장(`reference/field-bg-candidates/A-dark-night.png`) 을 사전 생성해 두었으며, 본 변경에서 양 플랫폼 assets 으로 옮긴다.

## Goals / Non-Goals

**Goals**

- 필드 프리뷰가 reference 톤의 야구장 일러스트 배경 위에 정보를 표시한다.
- 양 플랫폼이 동일한 정규화 좌표계로 10개 포지션을 정의한다.
- 현재 백엔드 응답으로 가능한 P/B 2명 이름을 정확한 위치에 표시한다.
- 기존 루상 점유 표시(1·2·3루) 는 배경 위 오버레이로 유지한다.

**Non-Goals**

- 외야 3 + 내야 4 + 포수 7명 라벨(라인업 API 부재 — 다음 change).
- 선수 사진/얼굴 표시(KBO 저작권 회피).
- 배경 이미지 동적 생성/팀별 커스터마이즈.
- 백엔드 변경.
- 워치 화면 필드 프리뷰.

## Decisions

1. **배경은 정적 PNG 1장** — higgsfield 다크 야간 톤(`A-dark-night.png`).
   - 이유: 동적 생성은 비용·속도상 부적합. 야구장 형태는 모든 경기에서 동일하므로 1장으로 충분.
   - 대안: 팀별 컬러 변형 PNG. 시각 임팩트는 있으나 자산 관리 비용↑, 우선 단일 자산으로 출시.

2. **정규화 좌표계(0.0~1.0)** 로 포지션 정의.
   - 이유: 양 플랫폼이 동일 좌표 데이터를 공유하면 정렬 어긋남 위험 최소. 화면 폭 변화에 자동 적응.
   - 좌표 정의 위치: 양 플랫폼 코드에 상수로 직접 정의(공유 JSON 도입은 과한 추상화 — 10개 좌표).

3. **현재 비어 있는 8개 포지션은 코드 레벨 placeholder 없음**.
   - 이유: 배경 이미지에 이미 베이스 점·다이아몬드 라인이 있으므로 빈 자리도 자연스럽게 보임. 빈 캡슐("—") 은 시각 노이즈.
   - 후속 change 에서 라인업 API 를 받으면 같은 좌표에 라벨을 채운다.

4. **이름 라벨 스타일은 기존 `LiveBadge` 캡슐과 동일 패턴**.
   - 흰색 텍스트 + 어두운 배경 캡슐 + 미세 stroke. reference 의 흰색 라벨 톤과 일치.
   - 폰트: `AppFont.microBold` (10sp 정도).
   - 위치: 좌표를 중심으로 라벨 위/아래 중앙 정렬.

5. **루상 점유 원은 새 좌표계로 이전**.
   - 1B `(0.62, 0.55)`, 2B `(0.50, 0.42)`, 3B `(0.38, 0.55)` 등(실제 값은 배경 이미지 기준 미세 조정).
   - 기존 `Canvas`/`Path` 코드를 제거하고 `Box`(Compose) / `Circle`(SwiftUI) 오버레이로 단순화.

6. **이미지 자산 추가 방식**.
   - iOS: `Assets.xcassets/BaseballFieldBackground.imageset` 폴더 + Contents.json + PNG. Xcode 가 카탈로그 폴더는 자동 감지하므로 `.pbxproj` 누락 위험 낮음. 단 새 .imageset 폴더는 group 등록 필요할 수 있어 빌드 검증으로 확인.
   - Android: `res/drawable/baseball_field_background.png` 1개 파일 — 빌드 시 자동 인식, 별도 등록 불필요.

## Risks / Trade-offs

- **[Risk]** 이미지가 8개 빈 포지션을 가진 채로 출시되면 사용자가 "왜 다른 선수 이름은 없지?" 라고 느낄 수 있다.
  → 1단계는 시각 임팩트 검증과 좌표계 정착이 주목적. 2단계(라인업 API) 가 가까운 미래에 따라오므로 영향 단기.
- **[Risk]** 배경 이미지 톤이 사용자가 선택한 응원팀 컬러와 충돌 가능.
  → 다크 톤은 다양한 팀 컬러와 무난한 대비. 추후 팀별 톤 분기를 후속 작업으로 검토.
- **[Risk]** 정규화 좌표가 화면 비율 변화에 따라 라벨이 베이스와 살짝 어긋날 수 있음.
  → 4:3 종횡비를 카드 자체에 강제(`AspectRatio(4f / 3f)` / `.aspectRatio(4 / 3, contentMode: .fit)`) 로 좌표가 일관되게 적용되도록 한다.
- **[Risk]** 이미지 파일 크기 증가로 APK/IPA 용량 영향.
  → 2K 해상도 PNG 는 3~8MB. 모바일 양쪽 합쳐 ~16MB 증가. 단일 자산으로 시각 임팩트가 크므로 트레이드오프 수용. WebP 변환으로 추후 50% 절감 가능.

## Migration Plan

1. higgsfield 로 생성한 `A-dark-night.png` 를 양 플랫폼 assets 로 복사.
2. 양 플랫폼 `BaseballFieldCard` 의 기존 `Canvas`/`Path` 다이아몬드 코드를 제거.
3. 배경 이미지를 카드 가득 채우는 형태로 표시(`ContentMode.fit` + 4:3 강제).
4. 정규화 좌표 10개 상수 정의. P/B 두 위치에만 현재 데이터로 캡슐 라벨 노출.
5. 1·2·3루 점유 원을 새 좌표로 오버레이.
6. 양 플랫폼 빌드 검증.
7. 시각 검증 — 라벨이 배경의 마운드·홈베이스 위치와 정렬되는지 좌표 미세 조정.

Rollback: 코드 revert + 이미지 자산 삭제. 백엔드 변경이 없으므로 데이터 마이그레이션 없음.
